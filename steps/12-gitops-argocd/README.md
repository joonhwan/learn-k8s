# 12단계 — GitOps (Argo CD)

> **이 단계의 문서는 아직 작성되지 않았습니다.** 진도가 여기에 도달하면, 그동안
> `PROGRESS.md`에 기록된 막혔던 지점을 반영해서 작성합니다. 아래는 다룰 범위입니다.

## 이 단계를 마치면

- Git 저장소를 단일 진실 공급원으로 삼아 클러스터 상태를 동기화할 수 있습니다.
- 클러스터에 직접 가한 변경이 어떻게 감지되고 되돌려지는지 관찰할 수 있습니다.

## 다룰 내용

- GitOps 가 무엇을 바꾸는가: `kubectl apply` 를 사람이 하는 방식과, Git 을 보고 클러스터가
  스스로 맞추는 방식
- Argo CD 설치와 접속 (초기 비밀번호, port-forward)
- Application 리소스로 저장소·경로·대상 클러스터를 선언하기
- 동기화 정책: 수동 동기화, 자동 동기화, `prune`, `selfHeal`
- **수동 변경 감지**: `kubectl scale` 로 개수를 바꾼 뒤 Argo CD 가 어떻게 반응하는가
  (03단계 5번 실습에서 남겨 둔 문제의 결말)
- App of Apps 로 여러 애플리케이션을 묶어 관리하기
- 이미지 태그를 어떻게 갱신하는가. 이미지를 만드는 파이프라인과 배포를 잇는 지점

## 이 단계의 전제

- 이 저장소가 Git 저장소로 초기화되어 있어야 합니다(00단계에서 이미 되어 있습니다).
- Argo CD 가 저장소를 읽을 수 있어야 합니다. 로컬 저장소만으로는 어려우므로, GitHub 등
  원격 저장소에 올리거나 클러스터 안에 간단한 Git 서버를 두는 방법 중 하나를 씁니다.
  어느 쪽을 택할지는 그 시점에 상의합니다.
- 이미지 문제: `kind load` 로 넣은 로컬 이미지는 Git 에 없습니다. GitOps 흐름에서 이미지가
  어디에서 오는지를 어떻게 다룰지 함께 정리합니다.

## 앞 단계에서 남겨 둔 질문

- **03단계 5번**: `kubectl scale` 로 바꾼 값과 매니페스트의 값이 어긋나는 문제를 남겨
  두었습니다. GitOps 에서는 이 어긋남을 `selfHeal` 이 자동으로 되돌립니다. 편리한 만큼
  위험한 면도 있으므로, 어떤 경우에 자동 복구를 켜야 하는지 함께 판단합니다.
