# 03단계 — 튜터가 틀렸던 지점

이 단계를 안내하기 전에 **반드시 읽으십시오.** 지난 학습에서 튜터(에이전트)가 잘못
설명했거나 혼동을 일으켰다가 학습자의 되물음으로 바로잡힌 내용입니다.

`README.md` 자체가 틀렸던 것은 README 를 고쳐 두었으므로 여기에 남기지 않습니다.

---

## 1. `maxUnavailable` 힌트를 줄 때 어느 파일인지 밝힐 것 (2026-08-31)

**무엇이 문제였나:** 실습 9(없는 이미지로 갱신하기)에서 "왜 옛 Pod 이 지워지지 않았는지
스스로 답해 보십시오. 힌트는 `maxUnavailable` 값에 있습니다"라고만 말했다.

**학습자가 어떻게 받아들였나:** `demo` 의 값이 `maxUnavailable: 0` 이라고 판단하고,
"0이므로 없어도 되는 Pod 수가 무한대"라고 해석했다. 값과 의미가 모두 뒤집혔다.

**왜 그렇게 되었나:** 두 가지가 겹쳤다.

- 이 단계에는 Deployment 가 둘 있고 값이 서로 다르다. `01-deployment.yaml` 의 `demo` 는
  `maxUnavailable: 1`·`maxSurge: 1` 이고, `02-deployment-strategy.yaml` 의 `demo-strict`
  가 `maxUnavailable: 0`·`maxSurge: 1` 이다.
- README 의 개념 절이 `maxUnavailable: 0` 을 먼저 설명한다. 그래서 그 값이 기본값처럼
  기억에 남는다.

**다음에 할 일:** 힌트를 줄 때 **파일명과 실제 값을 함께** 말한다. 그리고 이 필드가
"상한"이라는 점을 먼저 짚는다. 0은 가장 엄격한 값이지 느슨한 값이 아니다.

| 값 | 뜻 | replicas 3일 때 최소 가용 |
|---|---|---|
| `maxUnavailable: 0` | 하나도 빠지면 안 된다 | 3개 |
| `maxUnavailable: 1` | 하나까지는 빠져도 된다 | 2개 |

실습 9의 결과를 설명할 때는 두 경계선을 함께 계산해 보여 주면 한 번에 통한다.

```
replicas 3, maxUnavailable 1, maxSurge 1
  -> 준비된 Pod 최소 2개, Pod 총수 최대 4개
  -> 관찰 결과: 옛것 2개(준비됨) + 새것 2개(실패) = 4개, 양쪽 경계선에 동시에 닿아 멈춤
```

## 2. 환경이 느리다는 이유로 실습을 미리 잘라내지 말 것 (2026-08-31)

**틀린 판단:** "실습 8은 컨트롤 플레인이 불안정해서(`CLAUDE.md` 실행 환경 6번) 교대 과정을
관찰하기 어렵다"고 보고 건너뛰자고 제안했다.

**실제:** 학습자가 확인 질문 3번을 직접 확인하고 싶다고 해서 진행했더니 **관찰이 아주 잘
되었다.** 새 Pod 이 3~4초 만에 떴고 "새것 준비 → 옛것 제거" 순서가 세 번 모두 선명했다.
오히려 실습 9보다 빨랐다.

**왜 틀렸나:** 이 환경의 지연은 **일정하지 않다.** 스케줄러가 죽어 있는 구간에 걸리면 몇
분씩 멈추지만, 살아 있는 구간에 걸리면 정상 속도로 진행된다. 한 번 느렸다고 해서 항상
느린 것이 아니다.

**다음에 할 일:** 환경을 이유로 실습을 생략하려면 **한 번 해 보고 판단한다.** 미리
잘라내면 학습자가 확인할 기회를 잃는다.

## 3. 실습 8을 안내할 때 관찰 대상을 세 가지로 나눌 것 (2026-08-31)

실습 8은 확인 질문 3번("`maxUnavailable: 0` 과 `maxSurge: 1` 은 무엇을 보장하고 대가는
무엇인가")의 답을 눈으로 확인하는 자리다. 세 가지를 순서대로 짚으면 답이 완성된다.

**첫째, 교대 순서가 뒤집힌다.** 실습 9의 `demo` 와 나란히 놓고 비교한다.

```
demo-strict:  새것 Running 3s  ->  옛것 Terminating     (준비된 뒤에 지운다)
demo:         새것 ImagePullBackOff  ->  옛것 Terminating  (준비되지 않아도 지운다)
```

**둘째, `Terminating` 은 세지 않으므로 실제로는 상한을 넘는다.** watch 로그의 `AGE` 로
시각을 재구성하면 5개가 공존한 순간이 나온다. 이 앱의 `SHUTDOWN_DELAY` 기본값이 5초라
종료가 느리기 때문이다(`app/main.go:24`). 실무에서 자원을 계산할 때
`replicas + maxSurge` 만 보면 모자란다는 이야기로 이어 준다.

**셋째, 이 무중단은 아직 가짜다.** 여기가 핵심이므로 반드시 짚는다.

`02-deployment-strategy.yaml` 은 `READY_AFTER=5` 를 넣어 두고 `readinessProbe` 는 일부러
빼 두었다. 그래서 앱은 5초 뒤에야 준비되는데 쿠버네티스는 3초 만에 `1/1` 로 판정하고 옛
Pod 을 지운다. **`maxUnavailable: 0` 이 보장하는 것은 "준비되었다고 판단된 Pod 의 수"일
뿐이고, 그 판단이 실제와 맞는지는 별개의 문제다.**

```bash
POD=$(kubectl get pods -n learn -l app=demo-strict -o jsonpath='{.items[0].metadata.name}')
kubectl logs -n learn "$POD" --timestamps | head -5
kubectl get pod -n learn "$POD" \
  -o jsonpath='컨테이너 시작: {.status.containerStatuses[0].state.running.startedAt}{"\n"}'
```

이 간극이 08단계에서 `readinessProbe` 를 붙이는 동기가 된다. **전략과 프로브가 둘 다
있어야 진짜 무중단이 된다**로 마무리한다.
